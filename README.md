# MoviePilot-Plugins

MoviePilot 官方插件仓库，也是默认插件市场的源码与索引仓库：
<https://github.com/jxxghp/MoviePilot-Plugins>

当前开发目标是 MoviePilot V3。新插件开发者不需要先阅读 V2 文档，也不要在多份
“适配指南”之间自行拼接流程。

## 仓库负责什么

本仓库不是独立运行时：

- `MoviePilot` 负责插件加载、事件分发、API、服务、数据、工作流和 Agent 运行时。
- `MoviePilot-Frontend` 负责配置页、详情页、仪表板和 Vue 联邦组件渲染。
- `MoviePilot-Plugins` 负责插件源码、市场索引、图标、测试、文档和发布流程。

V3 新插件使用 `plugins.v3/<plugin_id_lower>/`、`tests/v3/<plugin_id_lower>/` 和
`package.v3.json`。V3 对旧插件的回退加载只用于兼容存量实现，不是新插件继续写入
旧目录的理由。

## 本仓库插件

### MusicTagWeb音乐库刮削

| 项 | 值 |
| --- | --- |
| 类名 / 目录 | `MusicLibraryScraper` / `plugins.v3/musiclibraryscraper/` |
| 配置前缀 | `musiclibraryscraper_` |
| 版本 | 0.4.0 |
| 元数据来源 | 插件内置的各平台公开检索接口（免部署 Music Tag Web），或切回 Music Tag Web 代为检索 |
| 图标 | `icons/avator.webp`（MTW 界面自带的头像图，已下载到仓库，市场走 raw 地址，不热链 MTW 实例） |

定时扫描音乐目录，把每个文件按「识别来源」拿去识别（内置源直连平台，MTW 模式交给它的
`/apimt/fetch_id3_by_title/`），再沿用 MP 原生音乐刮削链路写入标签与封面。

- 识别来源三档：`auto`（默认，配了 MTW 地址走 MTW、没配走内置源）、`builtin`、`mtw`。
  默认不能写成 `builtin` —— 老实升级的装机会一夜之间少掉酷我和 `smart_tag`、结果整体变样。
  两条路的候选折叠成同一形状，打分、阈值、逐项判定、写标签共用同一条链路，配置键也仍是
  `mtw_resource`（改名会让已存配置一起失效）；切换后端时两侧的源名单各存一份，来回切换
  不抹掉配到一半的选项。`/status` 与数据页回显两份：配置值（可能是 `auto`）和本轮实际生效的
  那一个 —— 只回显 `auto` 等于什么都没回显，用户看不出自己到底在问平台还是在问 MTW。
- 内置源（`plugins.v3/musiclibraryscraper/sources.py`，纯函数、不碰网络）：`netease`、`qmusic`、
  `kugou`、`migu`、`musicbrainz`。MTW 那几个源的真正客户端编译在 `.so` 里，抄不出来也不该抄 ——
  它转调的就是这批公开接口，按同一份契约重写即可。**内置源只发清洗后的「曲名-艺人」检索词，
  库内路径不出本机**；MTW 模式按它自己的前端契约仍带 `full_path` 作参考。
  歌词不由插件请求：宿主的 `LyricsChain` 已内置 lrclib 与 AMLL，插件再自己调一遍平台歌词接口
  只会多打一批请求，还要抢宿主选定的歌词策略。不做酷我：实测它的 `r.s` 检索接口对曲名索引
  恒不返回命中，www 接口要签名与 token —— 需要酷我的继续用 MTW 模式（配置页按生效后端
  只列出可用的那几个源）。
- 识别源为多选，**留空 = 当前来源的全部源**。MTW 模式另有 `kuwo`、`smart_tag`；实测 `qq`、
  `spotify`、`acoustid`、`all` 恒返回空候选，因此两种来源都不列入。某源已出满分
  （曲名+艺人+专辑 3/3）候选即停止后续查询。
- 候选选取规则（无排序配置项，插件自己判定）：按源顺序逐源查询，出现满分候选即停；都没满分
  则合并全部候选取最高分。分数为曲名 / 艺人 / 专辑 各 1 分（先做繁简与大小写归一，互相包含
  即算命中）；**同分时按源顺序、同源内按来源返回顺序取第一个**。最高分低于
  `min_score`（默认 3）就记为失败、不写入。用于匹配的本地身份优先读文件已有 tag，缺哪项
  按 `艺人/专辑 (年)/NN - 曲名` 目录结构兜底。
- 写入模式两档，都只作用于 MP 认识的字段（曲名、艺人、专辑、专辑艺人、年份、轨道号、
  碟号、封面、歌词）：
  - 只补缺（默认）：曲名+艺人+专辑+内嵌封面 四项齐全的文件按 mtime+size 记账直接跳过，
    一个检索请求都不发；缺哪项补哪项，已有非空标签保持不动。
  - 强制覆盖：忽略增量账、全库重扫，候选与现有标签不同就重写，封面重新下载内嵌，
    歌词强制重写。手工改过的字段会被替换；候选里没有的字段不会清空，
    插件不认识的自定义注释字段也不会删。
- 最终是否覆盖还要叠加宿主「设置 → 媒体刮削」的音乐三项策略，取两者中更强的一个：
  `tag_overwrite = 插件覆盖模式 or 宿主标签策略==覆盖`，`write_tags = 宿主标签策略!=跳过`。
  宿主默认是 标签仅缺失、封面仅缺失、歌词更优才换；把宿主标签策略设成「跳过」时，
  本插件两种模式都只写封面与歌词。
- 配置页不在单个选项下面挂长提示：来源、查询与选取规则、两档写入模式的后果、宿主策略叠加
  统一收在页面底部一个说明块里。v0.3.1 移除了 `mtw_select_mode`（只被解析回显、从不进请求，
  也不是 MTW 的入参，候选取舍一直由插件打分决定），已存过的这个键下次保存配置时自然消失。
- 数据页表格用 `v-data-table-server`：`items` 是服务端分页好的一页，`VDataTable` 的
  `pageCount` 按内存里的 items 长度算，一页 50 条时恒等于 1、下一页永久禁用（总条数要交给
  `items-length`）。页脚文案同样要直传 `items-per-page-text` / `items-per-page-options` /
  `page-text`：Vuetify 3 的 `VDataTable` 没有 `footerProps`（那是 Vuetify 2 的 API），写成
  `:footer-props` 会被当成未知属性丢掉，页脚一直是英文默认值。越界的 `offset` 会拿回空页、
  界面显示「该桶暂无数据」（重试成功后失败项少了几十条就会这样），取回空页时收敛到最后一页再取一次。
  `v-tabs` 的选中态要绑 `bucket`：写死 `model-value="failed"` 时选中态存在组件内部，
  换桶之后高亮还停在旧标签上。列一律 `sortable: false`：`/files` 只有按路径这一种服务端顺序，
  留着表头箭头点一下只重排眼前这一页 50 条，是一张既不全、又和总条数对不上的表。
- 扫描全程串行：周期任务、一次性任务、`/scan`、`/retry` 都走同一个带互斥入口，抢不到槽位就跳过
  而不是并发跑 —— 状态账是整读整写，两轮并行时后写完的会把先写的整本盖掉。
- 服务侧故障与「这个文件查不到」分开记：MTW 连不上、超时、401/403、接口 5xx，以及内置源
  全部不可达，都不写 failed 账、不涨 `retries`，连续 5 个文件栽在它上面就熔断中止本轮
  （且不 prune 账本）。否则 MTW 重启一次就给整库每个文件记一笔失败，连满 `MAX_RETRY=5` 轮后
  全体永久跳过。**只有没有任何源成功应答时**才算故障：某一个源正常返回（哪怕是空候选）就是
  确定答案「曲库查不到」，按文件失败记账 —— musicbrainz 限流、咪咕 500 这类单源故障很常见，
  据此熔断会让全库永远停在待处理。不在已知清单里的源（旧配置残留的 `qq`/`all` 或 API 写坏的数组）
  在读取配置时就过滤掉并只告警一次；配置里只剩当前来源不认识的源时退回该来源的全部源，
  而不是产出一轮零候选。内置源的另一条归因「内置识别源不可达」刻意不以 `MTW` 开头也不带「无候选」
  字样：账本按原因前缀分类，撞了就等于把内置源的故障记成文件失败、把限流摊成全库的重试额度。
- 内置源的响应形状不认识（平台改版）、业务码不对（风控）、2xx 但解不出对象（被网关或验证页截了），
  一律说成「这个源没给答案」并继续问下一个源，绝不当成「曲库里查不到」：前者该由插件这边修，
  后者会让用户白改阈值。正常的零命中才是结论。判定全在 `sources.py` 的纯函数里，形状变化
  一眼看得出来，也测得到。
- MTW 请求不能用宿主的 `post_json`：它内部那句 `if response:` 判的是 requests 的
  `Response.__bool__`（等价 `status_code < 400`），401/403/5xx 连状态码带错误体一起被折成 `None`，
  于是「JWT 过期」和「MTW 重启了」在插件眼里长得一模一样 —— 按形状兜底的分类只能把它认成不可达，
  v0.3.2 那条「鉴权失败强制重登一次再重试」永远走不到。插件改为自己拿 `post` 返回的 `Response`
  看状态码：401/403 → 鉴权失败（丢令牌、重登、重试一次），其它 4xx/5xx → 接口报错，
  连不上 → 不可达；三者都算 MTW 侧故障，但只有鉴权那一种会触发重登。响应仍要自己 `close()`。
  `/apimt/token/` 走 `expect_data=False`：成功登录的响应本来就没有 `data` 字段，按检索结果的
  形状兜底会把一次成功登录说成「MTW 不可达」。
- MTW 登录失败要静默 60 秒：每个文件、每个源在业务请求前都会先问一次令牌，账密错了或 MTW 关掉了
  `/apimt/token/` 时那是成倍增长的必然失败请求 + 一屏同样的错误日志。登录成功、或人改过地址账密时
  立刻作废这段静默期，别把「换了正确密码」也挡在门外。
  JWT 过期时间按令牌自身的 `exp` 算；换 MTW 地址或账密时丢弃缓存的令牌（那是上一个实例签发的）。
- 熔断对整盘扫描和大批量定向重试一视同仁：`/retry` 全部失败项同样可能几千个文件 × 全部源，
  MTW 真挂着时不能一路打到底；只有小批次才值得整批跑完。定向重试的汇总单独记在 `last_targeted`，
  不覆盖 `runs`，否则几个文件的重试会把整盘汇总刷成 `scanned=1`、`pending=0`。
- 汇总里的 `pending` 直接按账本算（本轮文件列表里既不在 `done` 也不在 `failed` 的那些），
  与同一时刻数据页的待处理桶是同一个口径：栽在 MTW 故障上的文件不落账所以仍算待处理，
  而上一轮记过失败、这一轮撞上故障的仍留在失败桶里 —— 用计数器加减很容易把后者多算一份，
  两个数字对不上号时看着就像有文件凭空消失。
- 单个文件不能带走整轮：落账每 60 秒一次，一轮跑到第七千个文件时崩掉，等于前面六千多个判断
  白做 —— 而崩点往往是确定性的（账本里的坏值、宿主 `ScrapingChain` 的内部异常），下一轮枚举
  走到同一条路径还是同一个位置，全库永远停在待处理。逐文件循环外面因此有一层保护：异常只影响
  那一个文件（既不记成功也不记失败、不涨 retries），连着出现按环境异常熔断，汇总多一档 `error`。
  账本里的 `retries` 也要归一成整数再进循环：它是 `int(prev.get("retries", 0))` 直接吃的那个值，
  `null`、`"三次"` 或旧版本写成的 dict 都会抛 `TypeError`；外层条目归一（v0.3.3）挡不住字段级坏值。
- 停止信号的两处漏口：复位（`clear()`）必须在锁内、占位之前，否则「置位 → 出锁 → clear」之间
  挤进来的 `stop_service` 会被抹掉，界面按了停止、日志里一句「收到停止信号」都没有；
  枚举里的 `break` 只退得掉当前这个库的 `os.walk`，不在外层库循环再挡一次，按了停止还在扫全盘，
  走完的目录还会被当成「这一轮扫过的文件」写进汇总。
- 投递一次性任务（`/scan`、「立即运行一次」）前要先看槽位：任务回调 3 秒后才跑，那时候抢不到槽位
  会静默跳过，不在投递前挡一下就会对着界面报「已提交」、实际一轮都没跑。
- 只处理宿主音频白名单（`RMT_AUDIOEXT`，宿主「设置 → 媒体刮削」可改）与本插件支持列表的交集：
  宿主不收的扩展名写标签时会被 `ScrapingChain` 直接拒成「刮削路径中没有支持的音频文件」，
  提前排除才不会白打请求、又把文件烧满重试次数后永久跳过。交集结果缓存 5 分钟 —— 宿主那份配置快照
  按需构建，而每个候选路径都要问一次「这个扩展名收不收」。读不到宿主配置（`None`）与宿主明确清空
  白名单（`[]`）必须是两个答案：前者按插件本地列表继续扫，后者一个文件都不碰并告警说明原因；
  两者都返回空列表时，要么把「被清空」误当成读不到去硬扫全库，要么把可用列表误判成空库。
- `.trickplay` 在目录级剪掉；枚举用 `os.walk(followlinks=False)`，`Path.rglob` 的 `**` 会跟随目录
  软链，库内一个回环软链能让枚举永不返回，而扫描槽位已被互斥占住。`followlinks=False` 只挡目录，
  **软链文件**仍出现在 `filenames` 里：宿主按插件递过去的路径写标签，库内一个指向库外的 `.flac`
  软链会被写穿出去，而 `/retry` 用 realpath 判定拒收的正是同一条路径 —— 两侧共用同一份
  realpath 基准（`_library_bounds` + `_target_in_library`）。排除目录也按 realpath 整棵剪枝：
  把它配成同一目录的别名或软链形式时，逐文件比字符串会整片漏掉，扫描照刮照写、`/retry` 与
  待处理桶却拒收。被跳过的库外软链按数量报一条 warning，配置页「会处理的文件」写明这条边界，
  否则用户只看到「发现 N 个文件」比目录里少、查不出为什么。
- 「四项齐全」里的内嵌封面不能只按帧名取：`tags.get("APIC")` 对 ID3 不可靠（APIC 是可重复帧，
  mutagen 的取法是 `getall("APIC")`，键还带描述），APEv2 的封面 key 更是 `Cover Art (Front)`，
  压根不在按帧名罗列的那份表里。判错的代价比判不出来更贵 —— 已刮齐标签、只差封面的 MP3/APE
  （真实曲库最常见剩下的缺口）会被补空模式永远判成「没齐」：每轮重打最多 7 次 MTW 请求，
  候选不达标还白涨 retries，五轮之后一个本来完整的文件被永久列成超限、再也刷不出来。
  现在通用图片接口（文件对象与 tag 容器两处）、`getall`、键名前缀/全名匹配一起用。
- 目录结构兜底的本地身份只认严格位于 `scraper_paths` 之下的目录：不加这层边界时
  `/media/music/01 - 轨迹.flac` 会得到 `album="music"`、`artist="media"`（库根的上一级），
  这两个假身份既被当搜索词发给 MTW，比对又是双向包含（`want in got` 也算命中），
  一个目录名就能白送两分；`min_score` 放宽到 1-2 时足以把错的艺人/专辑写进文件，而写标签
  不可回滚。边界用配置原文而不是 realpath：待判定的路径本来就是从这份配置拼出来的，
  库根自身是软链时 realpath 会让每个文件都判成「在库根之外」、目录兜底整体失效。
  猜不出来就留空判「未达阈值」，宁可少写也不写错。
- `min_score` 在服务端收敛到 1-3（越界按最近的一界执行）：配置页的 `min`/`max` 只是浏览器属性，
  原生表单和 `/api` 都能塞任意值，而两头都不可逆 —— 0 或负数会让只对上曲名的候选整库改写标签
  （写进文件无法回滚），大于满分则永远达不到阈值、整库都被记成失败。
- `force`（绕过增量账）与 `overwrite`（覆盖已有标签）是两个参数：界面上的「全量覆盖」两样都开，
  定向重试只绕过账本、保持配置的写入模式，不顺带替换手工改过的标签。
- `/retry` 与 `/music_scraper_retry` 命令走同一套路径判据：只接受 realpath 后落在 `scraper_paths`
  内、且不在 `exclude_paths` 内的音频文件，调用方传什么都改不到库外文件；命令入口也不再照着账本里
  已删除、已挪出库的路径白跑一轮（stat 失败会直接跳过、账本原样留着，看着像「重试过了还是失败」）。
- 勾选「立即运行一次」后的回写必须带齐全量配置键：宿主 `update_config` 是整体替换
  （`PluginInstanceOper.save_config_data` 直接 `record.config_data = deepcopy(config_data)`），
  只回写 `{"onlyonce": false}` 会把其余配置一起清掉。
- 状态账（done/failed/runs）写入 plugindata，按 mtime+size 增量跳过，扫描中按时间每 60 秒
  落一次账（整轮动辄数小时，中途容器重启不该丢掉已刮好的部分）—— 落账看时间而不是看条数，
  因为 plugindata 是单行 JSON，每次写都要整本重新序列化，大库上是 O(库大小) 的重复 IO；
  每个文件的 mutagen tag 也只解析一次（补空判定与匹配身份共用同一份）。
  数据页、`/status` `/files` `/retry` `/scan` API 与 `/music_scraper_status`
  `/music_scraper_retry` 命令都读同一份账；「待处理」桶是全库遍历做差集，最贵的一档，
  加 30 秒短期缓存，扫描开始与结束时作废。`/files` 不认识的桶名不再悄悄落到 `done` 那一档
  （回显仍是请求的那个名字，调用方拿到一批「已处理」的行却以为是自己传的桶），
  明确回 `unknown_bucket` + 空列表。
- 前置条件：只有识别来源走 MTW 时才需要「MTW 与 MP 挂载同一份音乐库路径 + 配置 MTW 地址账密」
  （MTW 会收到完整路径作参考，挂到别的库上就是把查到的元数据写进另一个文件）；内置源只需要
  音乐库路径和出得去网络的容器。扫描入口那句判据也必须认来源 —— 它此前硬要求 `mtw_base_url`，
  内置源模式下整轮静默跳过，日志只留一句「未配置 mtw_base_url」，看起来像插件没反应。
- 星期编号按宿主的调度器算，不按 crontab：宿主把这段 cron 交给 APScheduler，它的星期是
  0=周一…6=周日且上限就是 6，而 crontab 里 0/7 才是周日 —— 差一位，"每周日"的默认值会实际
  跑在周一，按习惯写的 7 又整条校验失败、连人配的时刻一起回落成默认。现在默认用星期名
  `0 3 * * sun`，只把单独的星期 7 就地换成 sun（保留其余字段），0-6 原样交给调度器、不猜意图；
  注册日志、`/status` 与状态命令都回显「下次触发在周几」—— 表达式里那个 6 落在哪天，
  光看字符串谁也读不出来。
- 失败要按原因聚合着给人看：`reason`/`score` 一直逐行记在账本里，但「最低匹配分数降一档能救回
  多少、该加哪个识别源」是按类做的决定，一屏 50 行翻页翻不出这个数。`/status` 新增
  `failure_reasons`（原因、个数、这类里最高的分、还有没有可重试的），数据页摘要与
  `/music_scraper_status` 直接给出「阈值降 N 分可命中」「均已超限不再自动重试」，
  命令输出同时补上汇总里已有的 `error` 档。
- 保存配置只弹一条通知：配置页走插件自己的 Vue 组件，宿主收到 `save` 后自己
  `PUT /plugin/{id}` 并弹「已保存」；配置页里那条 `toast.success('配置已保存')` 是重复的
  第二条，而且它在请求发出之前就说成功，保存失败了照样报已保存。现在配置页只把配置交出去，
  成与败连插件名一起由宿主报。
- 分桶切换要真的换数据：宿主注入给插件的 `api.get` **只认第一个参数**，第二个对象既不会拼成
  查询串也不会报错，直接被丢掉（豆瓣中心的插件都是把 `?page=…` 写进 URL 的）。写成
  `api.get(url, {bucket})` 时三个桶发出去的都是裸 `/files`，后端只能按默认值回「已处理」
  的第一页 —— 表现就是切换侧栏数据一模一样。查询条件现在由前端编码拼进 URL。
- 数据页与配置页是侧栏版式（参考豆瓣中心、PT监控室）：数据页左侧「概览 + 三个桶」，概览先给
  整轮结论（计数、最近一轮、本轮生效的配置、失败原因分布、流水线），核对具体文件再进某一桶；
  配置页左侧「流程总览 / 运行与写入 / 识别与匹配 / 音乐库范围」，先讲完一个文件从被扫到写标签
  经过哪些判断、各由哪个开关决定，再摆配置项 —— 这里每个开关最终都会改写音乐文件且不可回滚。
  两页流水线读同一份 `frontend/src/components/flow.ts`。宽度由 `layout` 事件向宿主申请
  （配置 74rem、数据 86rem，宿主默认 60rem 装不下侧栏加分页表）。
- 失败原因要写到「差在哪一项」：只记 `未达阈值（最低匹配分数 3）` + 分数 2，看不出是候选对不上
  还是本地根本没这项，而这两种要做的决定相反 —— 前者放宽阈值或改文件名，后者（整张 CD 压成
  一个 wav、目录里也没有曲名）降阈值救不回来，只能把它排出扫描范围。逐项判定一直算过、只是
  被丢掉了；现在 `hit / miss / 本地缺这项` 三态保留，原因带上「曲名未对上」「本地无专辑」，
  数据页与 `failure_reasons` 直接按它分类。本地读不出曲名的文件也不再记成「MTW 无候选」——
  那种是没问过，不是查不到。
- 失败要一行一行留在日志里：未达阈值/无候选的文件此前在日志里完全静默，一轮里几十个文件
  逐个问满 7 个源能连续跑上百分钟没有一行输出，看着就像卡死；现在每个失败文件一行，带原因、
  分数和这是第几次重试（`MAX_RETRY`）。
- 目录名、类名与配置前缀自 v0.2.x 起保持不变：MP 的 `config_data` 以配置前缀为键、
  `plugindata` 以类名为键，改名会让已配置的 MTW 地址账密和已积累的刮削状态账一起失效。

### 小爱音箱

| 项 | 值 |
| --- | --- |
| 类名 / 目录 | `XiaoaiSpeaker` / `plugins.v3/xiaoaispeaker/` |
| 配置前缀 | `xiaoaispeaker_` |
| 版本 | 0.2.0 |
| 元数据来源 | 无（不刮削，只播放）；设备与播放状态来自小米云端 Mina/ubus |
| 图标 | `icons/xiaoai.svg`（仓库自绘，市场走 raw 地址） |

把 MP 音乐库里的音频推送到小爱音箱上听：曲库索引与文本匹配、侧栏七栏页面（播放台 / 音乐库 /
歌单与收藏 / 定时任务 / 语音控制 / 账号与设备 / 配置）、设备分组多房间同步、睡眠定时与定时任务、
页面侧歌词、小爱对话监听驱动的语音口令，另有远程命令。播放地址由插件本机签发限时直链，
不经过媒体服务器转码。

- 小米云端的登录三步流程、`clientSign` 算法、ubus 请求体与需要走 `player_play_music` 的型号
  白名单，移植自 Songloft 的「智能音箱」插件 `songloft-plugin-miot`（Apache-2.0），并与
  Yonsm/MiService（MIT）、Music Tag Web（GPL-3.0）的同类实现交叉核对。**移植而非复制**：
  语言、运行时、错误处理与网络层都是本仓库的写法（宿主 `RequestUtils` + `requests` 会话）。
  不实现 MiIO/MIoT RPC —— 它只在个别触屏型号上用来走 `siid-aiid` 的 TTS action，普通
  `mibrain/text_to_speech` 已经能播报，而那条签名链路要额外的 xiaomiio serviceToken 与 HMAC
  细节，收益不抵复杂度。
- 登录：账密在服务端换 `serviceToken/passToken/userId`，票据只落本机插件数据。小米要图形验证码
  或邮箱/短信二次校验时，把码填回**同一次进行中的会话**继续跑（不是重新发起登录）；风控过不去
  还能在高级里粘贴整串 cookie，插件会拿 `device_list` 真跑一次校验，不通过就说清失败在哪一步，
  不假装登录成功。`/status` 只回「是否已设置密码 / 票据何时存的」，永不回显明文。
- 播放接口两档：`player_play_url` 推签名直链；硬件码命中型号白名单的（`LX05`/`LX04`/`L05B`
  等一批较新的音箱）走 `player_play_music`，配不准时用 `play_mode="url"` 覆盖。控制
  `player_play_operation`、音量 `player_set_volume`、播报 `text_to_speech` 失败回落
  `player_play_tts`。小米对同一句播报会返回设备码 `3012`，那被译成「可能已经播报」而不是报错。
- `/stream` 是**匿名**端点（音箱带不上 MP 的登录态），权限靠三重判据：HMAC-SHA256(`path|exp`)
  的前 32 位十六进制摘要 + `hmac.compare_digest` 常量时间比较、有效期、以及 `realpath` 必须落在
  配置的库目录内。支持 `Range`/206。越库、过期、签名不对分别是明确的 403 文案，不笼统说
  「链接无效」—— 用户要能分辨「地址填错了」和「这台音箱访问不到 MP」。签名密钥首次随机生成后
  留在本机，换密钥会让已发出的链接失效（可接受，不做兼容层）。
- 连播交宿主 `IntervalTrigger(20s)` 托管，插件不自建调度器。判「播完了」要同时满足：起播已过
  25 秒宽限，且**连续两次**读到停止 —— 起播初期云端会瞬时回一个 0 状态，单次判定会把队列
  一首一首烧掉。可选「连播时先播报下一曲」。
- 目标设备优先级：显式传入 > 配置的默认音箱（配置的默认音箱不在当前账号列表里时直接说明，
  而不是悄悄换一台）> 第一台在线 > 列表第一台。设备列表缓存 5 分钟，票据过期或网络失败时
  回落到缓存并带上失败原因。
- 外部访问地址取主程序设置里的**第一个**域名：主程序那一项允许逗号分隔多个，而一条直链只能有
  一个 host；host 里带空白的写法（`192.168.1.10 3000` 这类手误）直接判非法，`urlparse` 不会报错、
  只会拼出音箱必然拉不到的地址。
- 远程命令五个：`/xiaoai_status`、`/xiaoai_play <曲名或库内绝对路径>`、
  `/xiaoai_control play|pause|stop|next|prev|<序号>`、`/xiaoai_volume 0-100`、`/xiaoai_tts <文本>`。
  参数文本读宿主注入的 `arg_str`（不是 `arg`），失败也回一条消息而不是把异常抛到消息渠道里。
- 侧栏 Vue3 页面（`./AppPage`）分播放台 / 音乐库 / 歌单与收藏 / 定时任务 / 语音控制 / 账号与设备 /
  配置七栏，状态 5 秒轮询、页面隐藏时停；详情页 `./Page` 是同一批接口的紧凑版。`api.get` 只认第一个
  参数，`/browse`、`/search`、`/lyric`、`/playlist` 的条件由页面自己编码进 URL。配置页只发插件认识的
  字段（`/config` 缺省即保留原值、密码留空不覆盖）；「启用插件」与「显示侧栏入口」刻意不在这里改 ——
  那两项要宿主重新注册服务与导航，只有在插件管理页保存才会走到那条链路。
- 库内路径与音频内容不出本机：只有签名直链的 URL 交给音箱。可播放范围由「音乐库路径」与扩展名
  白名单限定，三处按同一条判据收敛（realpath 后必须落在库目录内、扩展名在名单里）：`/stream` 走
  `resolve_playable`，浏览与搜索本身就只从库根出发遍历，所以不会出现「列表里看得到、点下去 403」。
  搜索限深 6 层、命中 100 条就停：整库几万个文件时无脑 `rglob` 会先把请求拖死。
- 曲库索引（`library.py`）：一次扫盘把目录与 m3u 收成「歌曲 / 歌单」两张表，落进插件数据并带标签
  缓存做增量；没有标签就按文件名去掉序号推断，歌手从路径倒推。文本匹配是归一化 + 中文数字等价 +
  精确/等价/模糊三段打分，所以「播放周杰伦的稻香」「歌单范特西」都能落到具体文件；未命中会按需
  触发一次索引重建再判一次，而不是直接回「找不到」—— 但重建有最短 60 秒间隔，免得语音未命中变成
  扫盘循环。索引有条数上限（默认 10000），到数会明确说「被截断」而不是假装全看到了。
- 语音控制（`speech.py` + `voice.py` + `intents.py`）：读小米的对话记录（M01 这类走 ubus 的
  `nlp_result_get`）把说的话变成命令。轮询是**三态**的：`None` 表示没读到（不推进时间基线，下轮
  重来）、`[]` 表示读到了但没有新话、列表才是真的有新话 —— 把「读失败」当成「没说过」会把我没听见
  的话当成我说过，这是这套东西最容易做错的一处。监听器自带节流与失败退避（最长退到 30 秒），
  说过话之后的对话窗口内保持满速，追问才接得上。口令表逐类可开关，`POST /voice/test` 让任意一句话
  在**不接音箱**的情况下先看出会被判成什么；执行覆盖点歌/歌手/专辑/歌单/收藏/随机/刚才那首/搜索/
  暂停/继续/停止/上下曲/按序号切曲/音量与加减/静音/播放方式/定时停止/取消定时/查定时/播报。
- 语音记忆与 AI 兜底：近几轮的问答留在本机做指代（「换一首」「就要这个」），口令判不出来时可选把
  这句话连同候选交给 OpenAI 兼容端点判意图，或开自由对话；两个方向都只在显式开启时发出网络请求，
  API 密钥只落本机插件数据、配置页永不回显。从侧栏页保存「启用语音监听」会请宿主重建周期任务
  （`update_plugin_job`），否则开关只是写在配置里，并没有轮询真的跑起来。
- 播放方式五种（顺序 / 列表循环 / 随机 / 单曲循环 / 只播这一首），随机进度记录已播过去重、播完一轮
  自动重来；换一批曲目只清进度不清方式（说过「随机播放」之后切歌单还是随机）。睡眠定时能按分钟也能
  按首数，按首数是在「这一首真的播完」时判的，不是设个闹钟。队列、播放状态、定时、索引、监听、分组
  一并搭在 `/status.extra` 里回来，页面一次轮询喂满所有栏，而不是一栏一发请求。
- 设备分组：一条指令带动全组（播放、切曲、暂停、停止、音量、播报），全组共用一份队列/方式/定时；
  成员互斥 —— 把设备挪进新组会从旧组摘走，旧组不足两台即作废。组内某台离线只追一条「卧室：设备离线」
  的告警，不让整次操作判失败：音箱各自经云端收指令，没有帧级同步，轻微起播时差属正常。
- 定时任务：`weekly` 按星期几（0=周日）、`monthly` 按几号，到点执行播歌单 / 从某首歌播 / 停止 /
  设音量 / 设播放方式 / 开关语音监听。触发挂在既有的 20 秒巡检上并按分钟去重，同一分钟不会双发；
  执行日志留最近 200 条，`POST /tasks/run` 不等到点就能验证这条任务真能跑起来。目标可以是全部在线
  音箱、几台指定音箱或默认音箱，已被同组带动的成员不再作为独立目标各下发一次。
- 歌词走页面侧：同目录 `.lrc`/`.txt` 优先，其次音频内嵌歌词标签；编码按 `utf-8-sig`/`gb18030`/
  `big5`/`utf-16` 依次试而不是假定 UTF-8，多时间戳行会展开、`[ti:]`/`[ar:]` 这类头部不当歌词显示，
  没有时间戳的纯文本只做整篇展示。歌词文件软链到库外时一律不读 —— `/lyric` 和 `/stream` 用的是同一
  条库内判据。
- 三项**有意不做**：DLNA/UPnP 接收端（SSDP 组播与监听端口要在宿主容器里另开，第三方投送也无从认证；
  程序化投送的等价物是 `/play` 加 `/stream` 那对签名直链接口）、触屏音箱的本机歌词（要设备侧 Music
  API 与那块 UI，页面侧歌词已覆盖同一需求）、法定节假日调休（上游把 holiday-cn 数据集编进插件产物，
  装在宿主容器里的插件没有那份数据也没有更新渠道；要「只工作日 / 只周末」就分建两条任务勾不同周几）。

## 最重要的提交规则

- 插件目录名必须是插件主类名的小写形式，主类定义在目录的 `__init__.py`。
- 新增类和方法需要补充说明职责的注释。
- `plugin_version`、索引 `version` 和最新 `history` 必须一致。
- 当前版本历史置顶，所有历史按语义版本降序排列。
- V3 新代码优先使用 `app.sdk`；不要新增对宿主内部目录布局的无必要依赖。
- 宿主数据通过 Oper、Chain 或稳定 SDK 访问；不要直接操作宿主 Model，也不要自行持有
  `SessionFactory` 等裸会话工厂。数据库事务装饰器只用于插件自有表。
- 插件运行数据写入插件数据目录，不要写回源码目录。
- V3 第三方依赖写入插件 `pyproject.toml`，不提交插件 `uv.lock`；V1/V2 保留 `requirements.txt`。
- 第三方依赖安装在宿主共享环境，不能降级或覆盖 MoviePilot 核心依赖，也不要由插件直接执行包管理器。
- 测试放在仓库根 `tests/v3/<plugin_id>/`，不要放进插件源码目录。
- 提交前运行 Python 编译、版本门禁、相关测试和 `git diff --check`。

## 第三方插件仓库

第三方仓库建议 fork 本项目并保留相同目录和索引结构。MoviePilot 插件市场只读取
GitHub 仓库的 `main` 分支；仓库地址通过 `PLUGIN_MARKET` 配置，多个地址用逗号
分隔。

请勿开发用于破解 MoviePilot 用户认证，或提供色情、赌博等违法违规内容的插件。
