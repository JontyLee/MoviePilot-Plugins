# TagFlow音乐库刮削 使用说明

插件目录 `plugins.v3/tagflow/`，类名 `TagFlow`（v0.10.0 前为 `MusicLibraryScraper`），配置前缀
`musiclibraryscraper_`。这份文档讲判据与决策；界面上的文案只留最短的一句，为的是把
版面让给数据。改配置前先读「配置项」与「分数怎么调」两节。

- 目录名 / 类名 / 配置前缀 / 各项键名从 v0.1 起没动过。改它们会让已存配置与已积累的
  状态账一起失效（宿主按前缀存 `config_data`、按类名存 `plugindata`），所以更名只发生
  在展示层：`plugin_name`、图标、页面标题。
- 逐项变更历史看 `package.v3.json` 里本插件的 `history`，代码里那些「为什么这么写」
  直接写在对应常量的注释上，动代码前先读那几段。

---

## 它做什么、不做什么

周期扫描音乐目录，为每个文件向各音乐平台的公开检索接口要元数据，命中后沿用 MP 原生的
音乐刮削链（`ScrapingChain`）写标签、下封面。写进文件的只有 MP 认识的字段：曲名、艺人、
专辑、专辑艺人、年份、轨道号、碟号、封面、歌词。

不做的几件事，是刻意的：

- **不下载音频、不绕过会员或版权限制**。只发清洗后的「曲名-艺人」检索词，拿回的是文本
  与封面链接。
- **不替宿主决定歌词要不要覆盖**。歌词默认交给宿主的 `LyricsChain`；插件只在勾选
  「识别源补歌词」时，按候选自带的平台与歌曲标识多问一次歌词，把候选那一段补上，
  最终写不写仍由宿主策略定。
- **不碰插件不认识的自定义字段**，也不清空候选里没有的字段（不会把已有的 `composer`
  之类抹掉）。
- **不提供第二个后端**。v0.7 起识别源全部由插件直连平台，Music Tag Web 那套地址/账密
  已经移除（见「升级说明」）。

## 安装与首次运行

1. 市场装好插件，先在「插件配置」里填**音乐库路径**（一行一个目录）。填成库根
   （`/media/music`）就是整库扫；填成艺人的子目录就只扫那一片。
2. 保持**写入模式 = 只补缺**、**最低匹配分数 = 3**，先勾「立即运行一次」跑一轮。
3. 跑完到主界面「整理」分区的数据页看四个桶：已处理 / 有缺项 / 失败待重试 / 待处理。
   绝大多数文件应该落在「已处理」或「待处理」；「失败待重试」里成片的同类原因才需要处理。
4. 确认没有误改之后，再按「分数怎么调」决定是否放宽阈值，按需要把救不回来的文件排出
   扫描范围。

一次性跑整库会打不少请求：每个文件都把配置的源问完（不早停），最多 5 发。首轮之后的
增量扫描几乎不发请求。请求按源错峰发出、同一源也有最短间隔，为的是别让整库连成一台机器
的节拍 —— 慢的是额度而不是墙钟，一轮的耗时主要由写入与磁盘决定。

## 配置项

| 界面项 | 配置键 | 默认 | 决定哪一环 |
| --- | --- | --- | --- |
| 启用插件 | `enabled` | 关 | 插件是否加载、周期任务是否存在 |
| 整理区侧栏入口 | `show_sidebar_nav` | 开（缺键按开） | 主界面「整理」下是否出现数据页；关掉不影响周期扫描 |
| 立即运行一次 | `onlyonce` | 关 | 保存配置后立刻投递一轮扫描，随后自动回写为关 |
| 写入模式 | `mode` | `""`（只补缺） | 增量账是否生效、是否覆盖已有标签；`force_all` = 强制覆盖 |
| 执行周期 | `cron` | `0 3 * * sun` | 周期扫描时间 |
| 最低匹配分数 | `min_score` | 3 | 候选能不能用；服务端收敛到 1-3 |
| 识别源 | `resources` | `[]`（= 全部源） | 问哪些平台、按什么顺序问 |
| 音乐库路径 | `scraper_paths` | 空 | 枚举范围，同时是「目录兜底猜身份」的范围 |
| 排除路径 | `exclude_paths` | 空 | 从枚举里整棵剪掉 |
| 识别源补歌词 | `fill_lyrics` | 关 | 是否在候选不带歌词时多问一次 |

几条容易踩的：

- **`resources` 留空 = 全部源**，不是「一个都不问」。保存配置时如果没点名，回写的仍是
  空数组，这样以后新增的源会自动被用上；一旦点名，就固定是点名的那几个。
- **路径必须落在库里**。写标签是按路径落到真实文件的，所以指向库外的软链一律跳过，
  目录软链也不跟随。
- **`min_score` 越界不报错、按最近的一界执行**：写 0 或负数等于「只对上曲名也改写标签」，
  写大于 3 等于整库判失败。插件宁可收边界也不让这两种配置生效。

## 数据流转的七环

界面上那条流水线（配置页讲规则、数据页标出这一轮各环落了多少文件）对应的就是这七步。
光点走到哪一环，就是当前有多少文件正卡在那一环。

1. **枚举** —— 只处理「宿主音频白名单 ∩ 插件支持列表」的交集。宿主在写标签前会按
   `RMT_AUDIOEXT` 再过滤一次，插件先读它一眼求交集，否则不收的扩展名会白打满全部源、
   再被记一次刮削失败、烧满重试额度才永久跳过。Jellyfin 的 `.trickplay` 预览缓存目录
   整棵跳过。
2. **读本地身份** —— 优先用 mutagen 读文件已有的曲名/艺人/专辑/年份/轨道号；缺哪项就按
   `艺人/专辑 (年)/NN - 曲名` 的目录结构兜底。只有严格位于音乐库路径之下的目录才算
   艺人/专辑，库根本身的名字不参与猜测。猜不出来就留空 —— 宁可判「未达阈值」，也不拿
   目录名凑一个假身份去改写标签。
3. **增量判据** —— 只补缺模式下，曲名 + 艺人 + 专辑 + 内嵌封面四项齐全的文件按
   `mtime+size` 直接记账跳过，一个请求都不发；缺哪项补哪项，已有非空标签不动。
   强制覆盖则每轮全库重扫重问。
4. **全部源检索** —— 「识别源」里配的源每个文件一次问完，**不因某个源先出到 3/3 满分就
   省掉其余的源**。五个源并行发出、每发之前随机错峰 0~1.5 秒，同一源两次发问至少隔
   0.6 秒；单次超时 6 秒，所以一个文件的等待约等于最慢的那个源加上铺开的那点余量。
5. **打分与挑选** —— 曲名 / 艺人 / 专辑 各 1 分，繁简与大小写归一后互相包含即算命中。
   分数是**门槛**也是**主次**：最高分仍低于阈值就判失败、不写入、也不碰文件；过了门槛的
   候选不止一个时，比谁给得全（年份 / 音轨 / 碟号 / 封面 —— 这些不参与打分，却都是要写进
   文件、数据页会列成缺项的），一样全才按源顺序取先答的那一个。
6. **宿主原生写入** —— 命中后沿用 MP 原生音乐刮削链写标签、下载内嵌封面、写歌词。
   最终是否覆盖还要叠加宿主「设置 → 媒体刮削」里的音乐三项策略，取两者里较强的一方。
7. **记账** —— 成功进「已处理」；未达阈值进「失败待重试」；同一个文件最多自动重试
   5 次，之后进「超限放弃」，只有手动重试才会再问。服务侧故障不算文件失败、不烧额度
   （见「失败归因」）。

## 分数怎么调

满分 3 = 曲名、艺人、专辑三项都对得上。

| `min_score` | 含义 | 什么时候用 |
| --- | --- | --- |
| 3（默认） | 三项全中才写 | 一直这样。写标签不可回滚，宁可少写 |
| 2 | 曲名 + 艺人（或专辑）对上就写 | 库里有大量现场版、翻唱、别名，三项永远对不齐 |
| 1 | 只对上曲名也写 | 只在自己完全看得过来的一小片目录上用 |

调低阈值之前先看失败原因里的措辞：「曲名未对上」是候选不对，放宽阈值有意义；
「本地无曲名」是文件本身没给出身份（整张 CD 压成一个 wav 就是这种），放宽阈值救不回来，
该做的是把它排出扫描范围，或者先把目录拆成 `艺人/专辑/NN - 曲名`。

## 失败归因

数据页按原因聚合，每一行可以直接重试。判断的关键是**这次失败算不算文件的锅**。

| 原因文案 | 属于 | 记账 | 该做什么 |
| --- | --- | --- | --- |
| `未达阈值（最低匹配分数 N）：曲名未对上、专辑未对上` | 文件 | 记 failed，烧一次 retries | 文件名/标签本身对不上，或阈值太严 |
| `未达阈值（…）：本地无曲名` | 文件 | 记 failed | 排出扫描范围，或补目录结构；降阈值没用 |
| `本地读不出曲名（tag 与目录结构都没给出）` | 文件 | 记 failed | 一次请求都没发；同上 |
| `识别源无候选` | 文件 | 记 failed | 平台曲库里查不到，属确定答案 |
| `写入失败：…` | 文件 | 记 failed | 宿主刮削链被拒（权限、磁盘、路径不可写） |
| `识别源不可达` | 服务 | **不记 failed、不烧额度** | 连不上/超时/被风控页截了/解不出 JSON |
| 连续 5 个文件都是服务侧故障 | 服务 | 本轮熔断中止 | 剩下的留给下一轮，别在风控时段空打上千次 |

旧版本账本里的 `MTW 不可达` / `MTW 鉴权失败` / `MTW 接口报错` / `内置识别源不可达`
仍然按「服务侧故障」处理。账本存的是写下来那一刻的字符串，只认新名字会把升级前记下的
故障重新当成文件失败去烧额度。

超限放弃的文件，只要 `mtime+size` 不变，周期扫描就永远不再问；切一次「强制覆盖」或
手动重试才会再来。

## 各识别源现状

内置源是各平台 Web 端在用的公开匿名检索接口，端点、参数、请求头、响应字段沿用
Music Tag Web 的调用约定，但 `sources.py` 按同一批接口重写而非复制。不受开源许可覆盖，
也不承诺稳定。

| 源 | 能答 | 注意 |
| --- | --- | --- |
| `netease` | 曲名/艺人/专辑/封面/年份/音轨/碟号 | 中文库命中率最高，排在最前。音轨取条目里的 `no`（2026-10 实测《L.O.V.E.》的 Unity (Interlude) 回 `no=9`、`cd='01'`），但没有"专辑总曲数"，写进文件的是裸曲序而不是 `9/12` |
| `qmusic` | 曲名/艺人/专辑/封面/年份/音轨/碟号 | 音轨取 `index_album`。封面不在检索结果里，按专辑 mid 拼图片站地址。用的是免登录的 `DoSearchForQQMusicDesktop`；MTW 走的 Lite 那条只回 `item_v2`、字段更薄，所以它的 QQ 源经常不出候选 |
| `kugou` | 曲名/艺人/专辑/封面/时长 | **答不出年份与音轨**：实测条目里没有任何曲序字段（`no`/`index`/`track`/`cd` 这些键都不在），`trans_param` 全是版权、音质、偏移量这类播放侧的东西 —— 不是解析漏读，是接口没给。候选里同名版本多，靠逐项比对筛 |
| `migu` | 曲名/艺人/专辑/封面/年份/时长 | **答不出音轨**：`search_all.do` 的条目带着 `albums`/`isInDAlbum`/`dalbumId` 这类"属于哪张专辑"的字段，就是没有 `trackNo`。覆盖率低于前三。请求里的 `searchSwitch={"song":1,…}` 不能删：实测同词带与不带是 20 行 / 0 行 |
| `musicbrainz` | 曲名/艺人/专辑/发行/时长/MBID | **不带封面，也不带音轨**：检索响应里每条 release 只有 `title`/`status`/`date`/`track-count` 这些专辑级字段，`media[].tracks[].position` 要按 release 再取一次详情才有 —— 那是给每个候选多打一发。繁体与别名对得上，所以排在中文源之后当文本兜底；按官方要求自报身份 UA，超限返回 503 |

**音轨号只有 `netease` 与 `qmusic` 给得出**，而它不参与打分（打分只看曲名/艺人/专辑三项），
所以「这个源字段更全」这件事在过去常常赢不下挑选：两条都 3/3 时按配置顺序取先答的那一个，
带音轨的候选不会因为带音轨而多得分。现在满足门槛的候选之间比的就是完整度
（年份 / 音轨 / 碟号 / 封面），网易云与 QQ 的音轨因此会自己补上，不必再靠源顺序撞运气。
命中 kugou/migu/musicbrainz 且别处也问不出音轨的那批文件，缺的音轨只能由人在「编辑」里补 ——
文件名 `09 - Unity.m4a` 那个序号看着像答案，但拿它去写一个改不开文件的 tag 是猜的（数字开头
也可能是年份、碟号、卷号），本插件的规矩是猜不出身份宁可不动文件。

刻意没接的：

- **酷我** —— 匿名检索接口答的是「哪个录音在」，实测 `ALBUM` 与封面字段整片为空，排在最前
  的又常是伴奏、片段、演唱会串烧。命中要三项都对得上，这个源永远凑不齐第三项：默认阈值下
  一条也进不来，放宽到 2 分只是多一批对不上的候选来参与完整度比较。真要接得先按 `MUSICRID`
  逐个补专辑与封面，等于给每个候选多打一发；`www` 那个接口能给全，但要签名与 token。
- **Spotify / AcoustID** —— 前者要 client/secret 换 OAuth token 才有检索，后者要音频指纹
  （`fpcalc`）加应用 key。两个都不是「拿曲名艺人去问」的文本检索源。
- **`smart_tag`** —— MTW 里的 AI 辅助，没有可对齐的对外接口。
- **MusicBrainz 封面** —— 检索响应不带封面，为封面再追一次 coverartarchive 等于给每个
  候选多打一发。

## 隐私边界

- 发给平台的只有一个清洗后的检索词（`曲名-艺人`，互不包含才拼艺人）。**库内路径、
  目录结构、文件名都不出本机**。
- 每次请求最多取 10 条候选；再大只是多召回同类版本，判定靠逐项比对而不是候选数量。
- 日志里出现的是文件名与命中的曲名/来源，不写任何账密（v0.7 起本来也没有账密这一项）。
- 不上传、不下载音频，不调用需要登录态的接口。

## 周期与命令

- 默认 `0 3 * * sun`（每周日 03:00）。星期编号按调度器语义：**0=周一…6=周日**，和
  crontab 的 `0=周日` 差一位；写成 `7` 会被归一成 `sun`，写名字最没有歧义。界面会回显
  下次实际触发时间，配完看一眼就知道落在周几。
- 远程命令：`/music_scraper_status`（状态与按原因聚合的失败）、`/music_scraper_retry`
  （重试全部失败项）。
- 扫描只有一个入口，周期任务、`POST /scan`、`POST /retry`、「立即运行一次」都走带互斥的
  入口。两本账并发读写，后写完的会把先写的整本盖掉。
- 单个文件崩掉不会带走整轮：宿主 `ScrapingChain` 外面包了一层，异常既不记成功也不记
  失败，下一轮照原样再来。
- 整轮动辄数小时，中途按不小于 60 秒的间隔落账；容器重启不会把进度全丢掉。

## 接口

插件自带一组 `bear` 认证的接口，供 Vue 数据页与 Agent 调用：

| 接口 | 说明 |
| --- | --- |
| `GET /status` | 汇总、各环节计数、配置回显（生效的源列表）、最近失败按原因聚合 |
| `GET /files?bucket=done\|failed\|pending\|deficient` | 分桶分页查询，可带 `search`；`done` 桶另支持 `written=1` 只看本插件改写过的 |
| `GET /file?path=…` | 单个文件的现状：当前标签（含歌词文本）、还缺哪几项、本插件的改写记录；只读库内音频，读不出来说 `unreadable` |
| `GET /candidates?path=…` | 补齐弹层问源用：按配置的源名单**并行**问一遍（各组取该源分最高的一条，带分数与逐项命中、完整字段值、带封面的源另给 `cover_url`），单个源最多等 6 秒，同一路径 60 秒内重复打开直接吃缓存；另回失败账里记下的历史最佳；只认库内路径，本地读不出曲名说 `no_title` |
| `POST /retry` | `{paths:[…]}` 只重试指定文件，`{bucket:"failed",all:true}` 重试全部失败项。重试一律按**覆盖写**投递（v0.11 起）：只 force 不覆盖的话，失败项重刮一遍还是「只补缺」，源上的值再不对也一个字不动。待处理行的「立即刮削」也走这一条 |
| `POST /edit` | 手工补齐单个文件的曲名/艺人/专辑/年份/音轨号/歌词，另可带 `cover_url` 补封面（插件下载后按容器内嵌，已有封面被替换）；只写库内路径，空白字段不动，地址不合法或取不到图整笔退回。接口对库内文件一视同仁，界面上从 v0.14 起只对已处理/失败/有缺项给「编辑」 |
| `POST /scan` | 触发一次扫描，可带 `force` |
| `GET /config` / `POST /config` | 侧栏配置对话框用；GET 回的是**存储值**（留空的源仍回空），POST 是部分写：以当前全量做底、只覆盖传上来的键、不认识的键丢掉 |

侧栏那份配置为什么要插件自己做：宿主给 `./AppPage` 的 props 只有 `api/pluginId/navKey`，
没有 `initialConfig`，按插件管理页那套 emit 出去会被 `update_config` 的整体替换抹掉没显示
的键。

## 改写记录与逐项补齐

进度账里每个已处理文件都记着「本插件把它从什么改成了什么」（`done` 条目的 `set`）：写入
前后各读一次 tag 取差集，所以宿主按自己的策略拒了覆盖时，记录说的是文件现状而不是"打算
写什么"。封面与歌词只记有无，长值截到 120 字 —— 账本是单行 JSON，整库都存整段歌词会把
它撑肥。

数据页据此做三件事：

- **已处理桶把改写过的排在最前**（段内按最近一次改动倒序），行上直接挂「改写 N 项」和
  改了哪几项；开关「只看本插件改写」把它们单独筛出来，其余是宿主写的或往轮判定已齐跳过的。
- **点任意一行看详情**（v0.13 起操作列不再放「详情」按钮，整行就是入口）：改前 → 改后的差集、
  文件里现在写着什么、还缺哪几项。
- **列随桶走**（v0.13）：一个桶里每一行的状态都相同，所以没有「状态」列；「重试」那一列只有
  失败桶出现（其余桶这个字段本来就是空的）；中间那一栏按桶换名 —— 失败桶叫「原因/分数」，
  有缺项桶叫「还缺哪几项」，已处理桶叫「写入来源」，待处理桶不给这一列。每一列都给死宽度并
  配 `table-layout: fixed`（v0.14）：默认按内容摊时，文件名列里那条不换行的完整路径会把本列
  撑到自己满意，中间那栏被压成窄窄一条竖排 —— 最该看的内容反而最窄。
- **「有缺项」桶的补齐弹层先回填现值**：已有的字段带着值和"已填"标记，只有缺的那几项要
  人补；保存时只提交真正改动过的字段，不会把你没碰的值原样再写一遍。同名 `.lrc` 里的歌词
  也算"已有"，会带着"取自同名 .lrc"的标记填进去，留空则不改动。
- **弹层里可以直接「问源」再决定采不采纳**：点「获取候选」把配置的源并行问一遍（错峰只在
  整库连跑那条路上生效，这里人在等答案，直接发），每个源给出分最高的一条，带分数与
  曲名/艺人/专辑逐项命中；失败账里存过的历史最佳（当时分最高候选的摘要）一并显示在下方。
- **点候选卡片打开详情弹窗，采纳哪几项由人勾选**：弹窗按字段逐行列出「文件里现在是什么 /
  源上给的是什么」，默认勾上所有与文件不同的字段，也可以整行点「采纳这条」直接全收。
  点「应用所选」只把勾中的字段填进表单并说明填了几项 —— 采了不等于写了，仍然要按表单的
  保存差集落文件。字段现在覆盖曲名、艺人、专辑、年份、**音轨号**、歌词（v0.11 前候选带着
  音轨号也没有采纳入口，自动链路里也只有网易云和 QQ 音乐的检索结果带这个值）。
- **封面在这页直接补**（v0.13 起）：弹层里「封面」那一栏填图片地址，保存时插件下载并内嵌，
  文件里已有封面会被换成这一张；带封面的候选另有点「采纳封面」把地址填进表单。它和文本
  字段是两条写入路（文本走 mutagen，封面要取图再按容器内嵌），所以单独立一个键、成功失败
  单独回报：地址取不到图时**一个字都不写**，文本写成功而内嵌失败时会明说「封面内嵌失败」。
  此前这里写着「缺封面补不了，请用行上的重试」—— 重试是让识别源再刮一遍，人已经知道该用
  哪张图的时候，那条路绕且不由人。
- **「编辑」开给已处理、失败、有缺项三个桶**（v0.14 起收窄）：这三桶都是「插件已经判过、
  值就摆在那里」的状态，改哪一项都由人定。**待处理桶不给编辑**，那一桶是「还没轮到」而不是
  「写坏了要修」—— 文件里现在写着什么，插件一个字都还没核对过，手工填进去等于把没核对过的
  现值固化成结论。这一桶只给「立即刮削」（走的还是 `POST /retry`，动词按桶取），要动手早晚
  就让它现在问一轮，否则等下一轮自动处理。「重试」仍然只在失败桶出现。
- **「写入来源」只在真写过字时才印**（v0.14 起）：`done` 账对每一条都记着本轮的扫描来源，
  判定已齐跳过的、值由宿主自己写的那些 `set` 是空的 —— 以前这些行照样跟着「网易云」，于是
  出现「本插件改写 0 条」的筛选项旁边一排写入来源，界面自己跟自己对不上。现在这些行老实写
  「未改写」，改写过才在后面跟来源。

手工补齐同样进改写记录（没有扫描来源可沿用时标 `manual`），所以在这页改过的文件在「已
处理」里也找得回来。

## 升级说明（v0.14 待处理只给立即刮削，写入来源不再空口认账）

- **待处理桶的操作换成「立即刮削」**：v0.11 把「编辑」开给四个桶，是为了救「界面上看得见、
  动手没处动」，但待处理这一桶跟着一起开是开错了 —— 那儿的文件插件还没判过，弹层回填的是
  没核对过的现值，人照着它保存就等于替插件把结论定下来。这一桶从此只有「立即刮削」（复用
  `POST /retry`，覆盖写、与失败项重试同一个入口，只是说法按桶走），要么等下一轮自动处理。
  编辑仍开给已处理 / 失败 / 有缺项，「重试」仍只在失败桶。
- **「写入来源」要有改写记录才印**：`done` 账对每条已处理都记扫描来源，`set` 却只在真往文件
  里写过字时才非空。以前来源列不管三七二十一照印，最典型的一幕就是概览写着「本插件改写 0
  条」、列表里一排「网易云」—— 那不是数据错，是列名在骗人：没写，就没有「写入来源」。现在
  这些行写「未改写」，点开详情仍能看到那句「要么本轮判定已齐直接跳过，要么是宿主自己写入的」。
- **列宽写死**：文件名列 36%、中间那栏 28%、重试/大小 76px、修改时间 145px、操作 100~150px，
  外加 `table-layout: fixed`；路径那行的 480px 兜底随之删掉 —— 列宽既然由表头说了算，就不该
  再由一行路径说了算。
- 打分与挑选、记账口径、写入策略、问源节拍、封面那条链路都没动。

---

- **封面这一项从此可以动手**：补齐弹层原来写着「缺封面这里补不了，请用行上的重试」，而重试
  是让识别源再刮一遍 —— 人已经知道该用哪张图的时候，那条路既绕又不由人。现在「封面」一栏
  填图片地址即可：保存时插件下载并按容器内嵌（APIC / covr / WM/Picture / FLAC pictures 都
  交宿主那条写入链路，插件不自己认第二遍），文件里已有封面会被换成这一张。带封面的候选另
  有点「采纳封面」把地址填进表单，仍然要按「保存」才落文件。
- **三条口径跟着一起立**：地址只认 http(s)、限长度（`data:` 内联等于把任意载荷从接口塞进
  文件）；**图先取到手再动文件**，取不到就一个字都不写，否则「标签改了、封面没来」这种半截
  状态在账本上和全成功长得一模一样；文本写成功而内嵌失败时单独回报，不说成「已写入 N 项」。
  补成功后差集里出现「封面 无 → 有」，`missing` 重算，这一项从「有缺项」桶与徽标里掉出来。
- **表头按桶给**：分桶就是按状态分的，一个桶里每行状态相同，「状态」列等于把桶名重印一遍，
  删；`retries` 只有失败账里有值，「重试」列从此只在失败桶出现（以前它在那三桶里是一列空白，
  看着像坏了）；中间那一栏按内容换名 —— 失败桶「原因/分数」、有缺项桶「还缺哪几项」、已处理
  桶「写入来源」，待处理桶没得说就不给这一列。
- **操作列去掉「详情」按钮**：整行本来就是点开详情的入口（点操作列里的按钮不会连带弹层，这条
  规矩没变），按钮留着只占宽。桶名下面补一句「点任意一行看详情」，免得这条操作方式从界面上
  消失。
- **候选接口多带一个 `cover_url`**：地址不进 `fields` —— 那一层是文本标签名单，URL 混进去
  就会被当成曲名那类值写进标签。历史最佳仍只有摘要与「当时带不带封面」的布尔，账本里没存
  地址（要补封面就重新问一轮）。
- 打分与挑选、增量判据、记账与写入策略、问源节拍都没动。

## 升级说明（v0.12 挑「给得最全的那一条源」）

- **不再满分早停**：每个文件把配置的源一次问完，`min_score` 退回它本来的角色 —— 门槛，
  而不是排序依据。过去某源先出到 3/3 就停，后面的源根本没机会说话，于是「这一轮到底给文件
  补上几项」取决于谁排在名单前面。
- **同分之间比完整度**（年份 / 音轨 / 碟号 / 封面）。这一档最常偏袒的就是网易云与 QQ 音乐，
  因为只有这两家的检索接口给得出音轨号：以前它们即便排在后面也拿不到写入权（先答的裸候选
  已经满分），现在带音轨的那条胜出，缺的音轨会自己补上。完整度只在**同分**之间比，
  对不上三项的候选再全也不会被写进文件。
- **请求节拍打散**：一批之内每个源随机错峰 0~1.5 秒发出，同一个源两次发问至少隔 0.6 秒；
  单次超时仍是 6 秒。整库连跑时不再出现「每文件同一瞬间五发齐发」那种机器手感 ——
  最先被风控掐的总是排在最前的那个源。人工补齐（`GET /candidates`）不铺开，人在等答案。
  代价是每文件多等零点几到一点几秒，以及总请求量上升到「每文件固定问满配置的源」；
  熔断（连续 5 个文件服务侧故障即中止本轮）因此更要起作用。
- 增量账、写入策略、记账口径一行没动：改的只是「问哪些源、挑哪一条」。只补缺模式下
  四项齐全的文件照旧按 `mtime+size` 免问，所以这一轮的请求量涨在真正缺东西的那批文件上。

## 升级说明（v0.11 手工编辑流与问源提速）

- **改写记录里的「改写 0 项」有两种含义，先看这一轮是什么模式**。差集只认文件字节的变化：
  宿主「设置 → 媒体刮削」的音乐三项（标签/封面/歌词）默认 `missingOnly`，插件这一轮又不是
  覆盖写时，候选值与文件里的一样就一个字都不写 —— 这既不是失败也不该记成改写。想确认真动
  过没有，用数据页的「只看本插件改写」筛，或直接对单个文件用「编辑」弹窗核对。
- **10-18 之前记下的 `done` 条目里没有改写记录**：`set`/`set_ts` 这两个键是 v0.8 之后才补进
  账本的（本库首轮正是 v0.8 前的版本跑的），而增量命中缓存的文件不会重新记账，所以历史条目
  不会回填 —— 「没有记录」不等于「没动过文件」。
- `POST /retry` 与 `/music_scraper_retry` 命令改为按覆盖写投递（见「接口」）。
- `GET /candidates` 从逐源串行改为并行：原先五个源各等 10 秒，最坏一次要转四五十秒；现在
  单个源上限 6 秒、最慢的答完就齐，同一路径 60 秒内重复打开走内存缓存。（扫描主链路当时
  仍是「先出满分就早停」的串行问法，v0.12 起两条并成同一条。）
- 数据页：候选详情弹窗（逐字段勾选采纳）、音轨号与歌词可以采纳、四个桶所有行都能「编辑」
  （v0.14 起待处理桶撤回编辑，改成只给「立即刮削」）。

## 升级说明（v0.10 改名、缺项落账与问源）

- 插件改名 `MusicLibraryScraper` → `TagFlow`（插件 ID、类名、目录名一起换）。升级后第一次
  加载自动把旧类域名下的配置与四本账（done / failed / runs / targeted runs）整份接过来，
  旧域名原样留着不动 —— 不需要重新配置，进度也不会丢。
- `done` 条目多了 `missing` 键：这一轮核对过、文件现在仍缺哪几项。「有缺项」的徽标与列表
  改为直接数这个键（同一个口径，不会再出现徽标 125、列表 33），打开这一桶也不再全盘遍历
  逐文件读 tag。旧条目没有这个键：升级后**第一次**打开这一桶做一次并行补查（每个文件只读
  一次 tag，结果随账落盘），之后一直从账本直读；读不出来的按「已核对、无缺项」记空清单，
  不会把每次打开都拖成一次全库扫描。写入与手工补齐都会顺手刷新 `missing`。
- 失败条目多了 `best`：判失败当刻分最高候选的摘要（来源、分数、逐项命中），补齐弹层不用
  重打网络就能看到当时是谁给的。
- 新增 `GET /candidates`：补齐弹层里按配置的源名单现场问一轮候选，见「接口」与
  「改写记录与逐项补齐」。

## 升级说明（v0.8 改写记录）

`done` 条目多了 `set` / `set_ts` 两个键，接口多了 `GET /file`。往轮记下的条目没有这两个
键，按"没有改写记录"处理 —— 不会把宿主自己写过的文件说成本插件改的；从这一版起跑过的
文件才开始积累记录，所以升级后第一轮「只看本插件改写」筛出来的东西会比实际动过的少。

## 升级说明（v0.7 移除 MTW 后端）

v0.6.x 及之前可以把检索整个交给一个 Music Tag Web 实例，要配地址、账号密码，还要让它
和 MP 挂同一份库。现在这一层已经在插件里了，所以后端选项、MTW 地址与账密全部删除：

- 旧键 `source_backend` / `mtw_base_url` / `mtw_username` / `mtw_password` 不再被读取。
  升级后第一次加载会在日志里说明一次「你原来配的地址与账密去哪了」，下次保存配置
  （整体替换）就把它们清掉。
- 旧键 `mtw_resource` 里配过的源名单**读一次作兼容**，不会因为你改过名就整个退回全部源。
- 已积累的失败账、进度账都保留；旧文案的故障仍按服务侧故障处理。

## 排查

| 现象 | 先看 |
| --- | --- |
| 侧栏没有入口 | `show_sidebar_nav` 是否关着、插件是否启用；入口在「整理」分区，需要管理权限 |
| 一轮下来 `scanned` 是 0 | 音乐库路径填错，或宿主 `RMT_AUDIOEXT` 不收这些扩展名（交集为空，日志会说明） |
| 满库都是 `识别源不可达` | 平台限流或出网不通；本轮已熔断，等下一轮，不会烧重试额度 |
| 某一片目录全是「本地无曲名」 | 整张 CD 压成一个文件，没有逐曲边界；排出扫描范围 |
| 想改回来 | 标签写进文件就回不去。先备份，或用「只补缺」+ 阈值 3 重新跑 |
| 已处理一千多个，「本插件改写」一个都筛不出来 | 多半是历史条目没有改写记录（`set` 键 v0.8 之后才有，增量命中的不回填）；再看这一轮是不是补空模式 —— 候选值与文件里的一样，差集就是空的，这些行现在在「写入来源」列直接写「未改写」。核对单个文件用「编辑」弹窗（看得见现值也能改）；要插件带着覆盖写重问一轮，在配置里开「强制覆盖」再跑一轮，v0.14 起已处理行上没有「重试」按钮 |
| 组件加载错误 / 页面空白 | 前端产物在 `dist/`，与市场包一致才有效；宿主解析 `nav_key=main` 走 `./AppPage` |

## 上游与许可

- **Music Tag Web** —— <https://github.com/xhongc/music-tag-web>（`GPL-3.0`）。本插件的
  逐源查询、候选归一与统一打分以它为上游，候选仍折叠成它 `fetch_id3_by_title` 给出的那个
  形状；各平台公开接口的端点、参数、请求头、响应字段也是它先摸清的，`sources.py` 按同一批
  接口重写而非复制（那些平台的真正客户端编译在 `.so` 里）。同为 `GPL-3.0`，引用与再分发
  无许可障碍。v0.7 起插件不再调用 Music Tag Web 的服务端，也不需要它的地址与账号。
- **MusicBrainz** —— <https://musicbrainz.org>。内置源只取 `CC0` 核心数据（曲名、艺人、
  专辑、发行日期、时长、MBID），未读 `CC BY-NC-SA` 的标签/评分/注释；按官方要求自报身份，
  每个文件最多问一次并排在中文源之后（超限返回 503）。
- **网易云 / QQ 音乐 / 酷狗 / 咪咕** —— 各平台 Web 端在用的公开检索接口，不受开源许可覆盖、
  也不承诺稳定。只发清洗后的「曲名-艺人」检索词，不下载音频、不绕过会员与版权限制；
  长期或商用依赖前请自行确认平台服务条款。
