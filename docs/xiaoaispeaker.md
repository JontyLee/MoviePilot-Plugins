# 小爱音箱 使用说明

插件目录 `plugins.v3/xiaoaispeaker/`，类名 `XiaoaiSpeaker`，配置前缀 `xiaoaispeaker_`。
把 MoviePilot 音乐库里的音频推到小爱音箱上听。这份文档讲怎么配、以及每处判据为什么
这么定；界面上的文案只留最短的一句，为的是把版面让给音箱与队列。

- 目录名 / 类名 / 配置前缀 / 各项键名从 v0.1 起没动过。改它们会让已存配置与插件数据
  一起失效（配置由宿主按前缀存 `config_data`；登录票据、设备缓存、队列、收藏、签名密钥
  这些状态从 v0.5.9 起按键名存在插件数据目录的 `state/<键名>.json`，0600），更名只发生在
  展示层。
- 逐项变更历史看 `package.v3.json` 里本插件的 `history`；代码里那些「为什么这么写」
  直接写在对应常量的注释上，动代码前先读那几段。

---

## 它做什么、不做什么

做的：小米账号登录（三种方式）、曲库索引与文本匹配、本机签发限时直链推送到音箱、
侧栏运行视图（播放台 / 音乐库 / 歌单与收藏 / 定时任务 / 语音控制）、设备分组多房间同步、
睡眠定时、页面侧歌词、小爱对话监听驱动的语音口令，以及一组远程命令。播放地址由插件
本机签发，不经过媒体服务器转码。

刻意不做的四件事：

- **MiIO / MIoT RPC**。它只在个别触屏型号上用来走 `siid-aiid` 的 TTS action，普通
  `mibrain/text_to_speech` 已经能播报，而那条签名链路要额外的 xiaomiio serviceToken 与
  HMAC 细节，收益不抵复杂度。
- **DLNA / UPnP 接收端**。SSDP 组播与监听端口要在宿主容器里另开，第三方投送也无从认证；
  程序化投送的等价物是 `/play` 加 `/stream` 那对签名直链接口。
- **触屏音箱的本机歌词**。要设备侧 Music API 与那块 UI，页面侧歌词已覆盖同一需求。
- **法定节假日调休**。上游把 holiday-cn 数据集编进插件产物，装在宿主容器里的插件没有
  那份数据也没有更新渠道；要「只工作日 / 只周末」就分建两条任务勾不同周几。

## 安装与首次运行

1. 市场装好插件，在「插件配置」最上面把**启用插件**打开。这一项为什么必须做在插件自己
   这边：宿主投影侧栏入口前先调 `get_state()`，而这一项取的是插件配置里的 `enabled`；
   插件管理页那个开关写的是宿主自己的实例记录，插不进 `get_state()`。只在那儿打开，
   侧栏不会出现，周期任务也不会登记 —— 装好了但永远看不到入口的死结就是这么来的。
   保存时插件会顺带请宿主重建一次周期任务（`update_plugin_job`），不用重启主程序。
2. 第 1 步里登录小米账号（下一节三种方式任选其一），登成后音箱列表当场端出来，挑一台
   设为默认 —— 后端登录成功时已经强制刷过一遍设备，不需要再点「刷新设备」。
3. 第 2 步填**音乐库路径**（一行一个目录）与**外部访问地址**（音箱能访问到的 MP 地址）。
4. 侧栏「播放台」点一首试试。第一首不通，先看「排查」。

没登录、没取到音箱时第 2 步整个收起来（那些配置在拿到音箱之前改了也无从验证），但收起
来不能变成死路：「启用插件」与「显示侧栏入口」永远留在最上面可编辑，第 2 步旁边也给
一句「我知道，仍然直接编辑其他配置」。

## 登录

三种方式地位相同，任意一种登成都行；配好的票据只写进本机插件数据，接口永不回显。
登录入口只在「插件配置」的第 1 步出现一次。

### 一、账号密码

在配置页填账号密码点「登录」：**先保存再发起**。后端只认配置里那一份 —— 票据过期要
重登、语音轮询要换票，都从配置读，只在请求体里带一次等于没存。

登录在服务端跑小米那三步，换回 `serviceToken` / `passToken` / `userId`：

- `deviceId` 首次生成后就固定并存进插件数据，每次登录都复用。小米把它当设备标识，
  每登一次换一个新的，就等于每次都从「新设备」发起 —— 于是要么每次都要验证码，要么
  把已经存下的 `passToken` 判失效。
- `serviceToken` 取的是重定向链**最后一跳自己那条 Set-Cookie**，不是同名 cookie 的
  回落值。别的 `sid` 早就塞过一个同名 cookie，取错的那张票会一直 401，而且看起来
  像「密码错了」。

小米判定新设备或可疑登录时会停下来要验证码，页面按状态分支：

- `need_captcha`：回一张图形验证码，照图填进去提交。
- `need_verify`：小米给的 `notificationUrl` 只是「这步校验在哪儿做」的地址，**码不会
  因为它自己寄出去**。插件按小米 App 抓到的链路点名发码：先 GET 那个地址把身份会话
  建立起来，再 GET 同一个 `context` 的 `/identity/list` 问小米要哪种方式（`flag=4`
  手机短信、`flag=8` 邮箱），然后 GET `identity/auth/verifyPhone` / `verifyEmail`
  触发校验，手机那条还要补一次 POST `sendPhoneTicket` 才是真正把短信发出去。页面据
  `flag` 说明码发往手机还是邮箱，把收到的码填进来提交即可（提交走
  `verifyPhone`/`verifyEmail` 的 POST，少任何一步码填什么都过不去）。
  发码这几步用的是登录会话自己的 cookie，和浏览器里那份是两回事，不会互相顶掉。

**验证码要续跑在同一次进行中的会话里**（请求体只带 `code`）：重新发起会让小米把上一次
的努力全部作废。但**等不来码时反过来必须重新发起**（页面的「重发验证码」就是
`resend=true`，它会整条链路重跑一遍，重新寄一次码）。发码那几步任何一步被小米拒了，
提示里会写清楚是哪一步（`identity/list` 打不开 / `sendPhoneTicket` 被拒），别把它当
「密码错了」。

### 二、扫码

切到这个标签就自动取一张二维码（旧会话还在等的除外），页面列三种状态：等待扫码、成功、已过期。

- 二维码由 `sid=mijia` 的会话取回，有效期取小米给的 `timeout`（观察到 300 秒），页面
  挂倒计时条。**过期就点「换一张」**，旧码扫了也不会生效。
- 确认结果由页面驱动轮询：一次请求在插件侧最长挂 8 秒（小米的长轮询本来就挂着等），
  所以是串行问、不并发；页面一关就没有后续请求，插件不留没人收结果的后台循环。
  **只有「获取二维码」那次响应带图片**，后续轮询回的是状态与时限，页面沿用第一次那张
  图 —— 二维码属于这次会话，不属于某一次请求。
- 单次非零 `code` 只当长轮询自己的重连抖动，连续两次才判过期 —— 一次就判死会把正在
  扫码的人赶走。客户端超时同样是常态而不是失败。
- 扫过并在手机上确认后，小米回 `passToken` / `userId`，插件拿它现换 `micoapi` 的
  serviceToken，`deviceId` 沿用扫码这一套（票据绑在设备标识上，中途换一个反而更像异常登录）。
- **二维码的内容（`loginUrl`）是一次性的登录凭证，只留在服务端，绝不回给前端** ——
  回出去等于谁拿到都能替本人把这次登录做完。
- 这条路不走密码，也就绕开了「新设备登录」那套风控；密码反复登不上时，同一个账号通常
  扫码能过。扫码不知道账号叫什么，票据里留 `userId` 供界面标出这是哪个账号。

### 三、Cookie 票据

前两种都不方便时的兜底，只填两项：浏览器 cookie 里的 `userId` 与 `passToken`。

- **先在浏览器里登录 `https://account.xiaomi.com`**，从 DevTools 的 Cookie 里复制这两项的**值**
  （不是整串 cookie —— 整串会被当场拒绝并说明只填值，免得换票失败后人去猜哪一项错了）。
  `passToken` 只有 `account.xiaomi.com` 这个域的 Cookie 里才有，从 `i.api.xiaomi.com`、
  `micoapi` 之类的页面复制到的都是别的会话的票，小米一律判 `code=70016 登录验证失败`。
- 填进来后拿 `passToken` 现换一张活票，**换到了才说明这串凭据真的有效**，本机也顺带有了
  能静默续期的长期票据。小米对坏票据只给一个码（`70016` / `desc=登录验证失败`），不会说
  「你粘错了」，所以这里不接受直接用浏览器里那张 `serviceToken` 兜底：它通常已经躺了十几个
  小时，硬拿去用就是「显示成功、事事 401」。
- 值是百分号编码的（从原始请求头里复制会带上 `%3D`）会自动解开一次 —— `passToken` 本身
  是 base64，不含 `%`，看见 `%` 就说明那是编码过的。
- **小米按请求「自称的是什么客户端」决定认不认这张票**，所以这一步试两种标识：手工填的
  票先按 iOS passport（`sdkVersion=3.9`，和上游 MiService 一致）问 —— 浏览器里那张本来就
  是网页会话 mint 的；被拒再用 Android 米家（`sdkVersion=3.8.6`）补问一次。扫码换来的票
  来路是 Android 米家，就按这个顺序反过来试。认不认得住日志里各写一行，命中第二种时页面
  不受影响。
- **这两项和账密一样只发给本插件：不进日志，接口也不回显。**

### 过期、退出与隐私

- 状态里的 `token_expired` 只说明票据到期。续期是自动的（`passToken` 还在就能重铸
  `serviceToken`）；`refresh()` 失败时按登录方式给提示 —— 扫码登的会说「请重新扫码」，
  不会让你去找一个从来没填过的密码框。
- 「退出登录」清票据、清缓存的设备列表、清进行中的扫码会话。
- **账号在接口与页面上都只回掩码**（`13****34`、`ab***@example.com`，另有
  `username_set` 说明存没存过）：`/status` 每 5 秒把整份配置带回侧栏，明文账号名等于
  把手机号长期挂在任何能看到这块页面的人眼前。写回时带 `*` 的值一律当作「没改」，
  配置页那格也不预填掩码，免得一次保存把真账号覆盖成打不上的串。密码永不回显，只回
  `password_set`。
- `/login` 整段被包起来：小米那条链路上的任何异常都折成 `state=failed` 带一句能看懂的
  原因回给页面，原文进插件日志 —— 只回「登录失败」等于让人去猜是密码错、风控还是代码坏了。

### 登录失败怎么读

| 页面上的话 | 含义 | 下一步 |
| --- | --- | --- |
| `小米拒绝了本次登录：code=…，说明：…` | 账密不对或被风控挡下 | 核对账号；反复如此就改扫码 |
| 卡在图形验证码 | 小米把它当新设备 | 照图填码提交；反复填不过就改扫码 |
| `验证码已发往手机短信/邮箱…` | 二次校验会话已建立、码确实寄出去了 | 查收后填进来提交；等不到点「重发验证码」 |
| `验证码没能发出去（…）` | 小米拒了发码那几步（`identity/list`、`verifyPhone`、`sendPhoneTicket`） | 点「重发验证码」再试一次；仍不行就改扫码 |
| `… 请重新扫码` | 扫码登的票过期了，且不能靠密码续 | 切到「扫码」重新来一次 |
| 小米云端业务鉴权失败（401/403） | 票据过期，或 Cookie 那两项填的是死票 | 重新登录一次 |
| `passToken 换票失败：…code=70016…` | 这对 userId/passToken 小米不认 —— 多半是从别的域（`i.api.xiaomi.com` 等）复制的，或那次网页登录已被作废 | 重新登录 `account.xiaomi.com`，从**该域**的 Cookie 复制这两项的值；仍不行就扫码 |
| `云端受理但设备返回 code=…` | 登录没问题，是音箱侧拒了这条指令 | 看下一节「播放与接口选择」 |

## 播放与接口选择

- 播放接口两档：`player_play_url` 推签名直链；硬件码命中型号白名单的（`LX05` / `LX04`
  等一批较新的音箱）走 `player_play_music`。白名单判错时用 `play_mode="url"` 强制覆盖。
  设备行上标了「该型号需走 play_music，直链可能被当成电台播放」的就是命中白名单的。
- **格式与接口是两件事**：`player_play_url` 实际只稳当吃 mp3 —— 把 m4a（`audio/mp4`）或
  flac 的直链推过去，多半是云端回 `code=0` 「受理了」而设备一声不出，看起来像地址不可达、
  其实是解码器不接。`player_play_music` 走的是音箱自己的音乐管线，编码兼容面宽得多，库里
  以 m4a/flac 为主时先切这一档。
  旁边那套 songloft 不能作为「音箱吃得了 flac」的反证：它日志里唯一一次音箱成功取流
  （`GET /api/v1/songs/881/play`，`status=206`、`content_length=3376726`，约 115 秒取完）
  取的那个文件本身就是 3.3MB 的 **mp3**，全量日志里也只有这一首被音箱取过。
- **一首 mp3 都没有时**，打开配置页的「非 mp3 现场转成 mp3」：`/stream` 边放边用本机
  ffmpeg 转成 mp3 再回给音箱（上游 songloft-plugin-miot 的 `force_mp3` 同一做法）。三个
  边界：转码是流式的、长度未知，所以这一条**不支持拖动进度**（`Accept-Ranges: none`，也不
  带 `Content-Length`）；机器上没有 ffmpeg 时插件直说并照旧播源格式，不会因为开了关反而
  把本来能放的弄坏；本来就是 mp3 的不经 ffmpeg。转码只在插件本机发生，音频不出这台机器。
  代价是每个在听的连接起一个 ffmpeg 进程，所以默认关着。
- 控制 `player_play_operation`、音量 `player_set_volume`、播报 `text_to_speech`
  （失败回落 `player_play_tts`）。小米对同一句播报会返回设备码 `3012`，那被译成
  「可能已经播报」而不是报错。
- 目标设备优先级：显式传入 > 配置的默认音箱（默认音箱不在当前账号列表里时直接说明，
  而不是悄悄换一台）> 第一台在线 > 列表第一台。设备列表缓存 5 分钟，票据过期或网络失败
  时回落到缓存并带上失败原因。

## 限时直链的安全

`/stream` 是**匿名**端点（音箱带不上 MP 的登录态），权限靠三重判据：

1. HMAC-SHA256(`path|exp`) 的前 32 位十六进制摘要，用 `hmac.compare_digest` 常量时间比较；
2. 有效期（`stream_ttl`，默认 3600 秒）；
3. `realpath` 必须落在配置的库目录内。

三者打包在**唯一一个**查询参数里：`/stream?k=<exp>.<sig>.<base64url(path)>`。这不为了简洁，
是为了能出声：小米云端会改写我们交给它的 URL，实测推过去的是
`…flac&exp=1792950245&sig=f0c2…`，音箱发回来的是 `…flac%20exp=1792950245%20sig=f0c2…`
—— `&` 变成了空格，于是服务端只收到一个 `path`（尾巴还粘着 `exp`/`sig`），签名必然对不上，
每首都是 403。所以这条链的值只用 base64url 字母表（`-`/`_`，不含 `%`、`+`、`&`、空格），
中间任何一层再编码或解码都动不了它，也不用再猜对方做了什么。

响应头里也不允许出现原始文件名：HTTP 头按 latin-1 编码，中文歌名直接塞进
`Content-Disposition` 会让框架在发头时抛 `UnicodeEncodeError`，取流请求变成 500（音箱表现为
反复重取、始终不出声，而且只有非 ASCII 文件名才踩得到）。这里给 ASCII 兜底名，原名走
RFC 5987 的 `filename*=UTF-8''`；测试桩现在也照框架那样编一遍头，这类 bug 才不会又溜过去。

支持 `Range` / 206。**音箱发的几乎都是 `Range: bytes=0-`（要整首），这一句也按 206 回**
并带上覆盖整首的 `Content-Range`：本机 songloft 的访问日志里，同一台音箱取那首能出声的歌，
回的就是 `status=206 range="bytes=0-" content_range="bytes 0-N/N"`；插件原先把「要整首」
判成不算分段请求而回 200，有些固件会把 200 这条当成不可分段的音频而不去解码。越界的
起点（`bytes=99999-`）不算这一类，仍按「从头播」回 200 整文件。
越库、过期、签名不对分别是明确的 403 文案，不笼统说「链接无效」——
要能分辨「地址填错了」和「这台音箱访问不到 MP」。签名密钥首次随机生成后写进插件数据目录
（`<数据目录>/state/secret.json`，0600），换密钥会让已发出的链接失效（可接受，不做兼容层）。

库内路径与音频内容不出本机：只有签名直链的 URL 交给音箱。可播放范围由「音乐库路径」
与扩展名白名单限定，三处按同一条判据收敛（realpath 后必须落在库目录内、扩展名在名单里）：
`/stream` 走 `resolve_playable`，浏览与搜索本身就只从库根出发，所以不会出现
「列表里看得到、点下去 403」。

外部访问地址取主程序设置里的**第一个**域名：主程序那一项允许逗号分隔多个，而一条直链
只能有一个 host；host 里带空白的写法（`192.168.1.10 3000` 这类手误）直接判非法 ——
`urlparse` 不会报错，只会拼出音箱必然拉不到的地址。

## 配置项

| 界面项 | 配置键 | 默认 | 作用 |
| --- | --- | --- | --- |
| 启用插件 | `enabled` | 关 | `get_state()` 的眼中是否启用；侧栏入口与周期任务都取决于它 |
| 在「发现」显示侧栏入口 | `show_sidebar_nav` | 开（缺键按开） | 是否投影侧栏页 |
| 小米账号 / 密码 | `username` / `password` | 空 | 账密登录用；回显只有掩码与 `password_set` |
| 默认音箱 | `default_device_id` | 空（= 第一台在线） | 侧栏播放台与远程命令的作用对象 |
| 音乐库路径 | `music_dirs` | 空 | 一行一个目录；浏览、搜索、索引、`/stream` 的边界 |
| 外部访问地址 | `base_url` | 空（取宿主域名） | 直链的 host，音箱必须能访问到 |
| 播放接口 | `play_mode` | `auto` | `auto` 按型号白名单选，`url` / `music` 强制 |
| 可播放扩展名 | `audio_exts` | 空（内置名单） | 白名单 |
| 非 mp3 现场转成 mp3 | `force_mp3` | 关 | `/stream` 用本机 ffmpeg 边放边转，见「播放与接口选择」 |
| play_music audioID | `audio_id` | 空（内置默认） | 走 `player_play_music` 时的音频标识 |
| 播放前设置音量 | `default_volume` | 0（不改） | 每次起播前拉一次音量 |
| 直链有效期（秒） | `stream_ttl` | 3600 | `/stream` 的 `exp` |
| 队列自动连播 | `auto_next` | 开 | 宿主 `IntervalTrigger(20s)` 托管的续播 |
| 播放时常亮 | `keep_light` | 关 | 部分型号会息屏 |
| 连播时先播报下一曲 | `tts_announce` | 关 | 切曲前 TTS 报曲名 |
| 开启语音监听 | `voice_enabled` | 关 | 读小爱对话记录变命令 |
| 监听哪些音箱 | `voice_devices` | 空（= 默认音箱） | 逗号分隔设备标识 |
| 轮询间隔（秒） | `voice_poll` | 2 | 2-30，失败自动退避到 30 秒 |
| 命中前先打断音箱 | `voice_interrupt` | 开 | 正在放歌时先把话说清楚 |
| 搜索期间的提示语 | `voice_hint_tts` / `voice_hint_text` | 关 / 「正在搜索，请稍候」 | 找曲要几秒，先给一句反馈 |
| 播报执行结果 | `voice_reply` | 开 | 成功失败都回一句 |
| 记住刚才那首 | `voice_memory` | 开 | 支撑「再播一遍」「就要这个」 |
| 口令未命中交给 AI 判定 | `ai_enabled` | 关 | 借用主程序已配好的助手，插件不另存 key |
| 没命中当聊天 | `ai_chat` | 关 | 说完 2 分钟内可追问 |
| AI 超时（秒） | `ai_timeout` | 6 | 2-30，真的当成 `wait_for` 的 timeout |
| 最多入库多少首 | `library_limit` | 10000 | 到数会明确说「被截断」 |
| 自动保鲜周期（分钟） | `library_refresh` | 60 | 0 = 只手动重建 |

口令表不在这张表里：它不是 `ConfigInfo` 的字段，走 `/commands` 读写，分两个文件落在
`state/` 下 —— `voice_commands.json` 是逐类开关，`voice_words.json` 是用户加的说法与被藏
起来的内置词。

`ai_ready` / `ai_provider` / `ai_model` / `ai_message` 不是配置，是宿主
「设定 → AI 大模型」的读数，只在 `/config` 与 `/status.extra` 里回给你看。

## 曲库索引与文本匹配

`library.py` 一次扫盘把目录与 `.m3u` 收成「歌曲 / 歌单」两张表，落进插件数据并带标签
缓存做增量；没有标签就按文件名去掉序号推断，歌手从路径倒推。

文本匹配是归一化 + 中文数字等价 + 精确/等价/模糊三段打分，所以「播放周杰伦的稻香」
「歌单范特西」都能落到具体文件。未命中会按需触发一次索引重建再判一次，而不是直接回
「找不到」—— 但重建有最短 60 秒间隔，免得语音未命中变成扫盘循环。搜索限深 6 层、
命中 100 条就停：整库几万个文件时无脑 `rglob` 会先把请求拖死。

## 队列、定时与设备分组

- 连播交宿主 `IntervalTrigger(20s)` 托管，插件不自建调度器。判「播完了」要同时满足：
  起播已过 25 秒宽限，且**连续两次**读到停止 —— 起播初期云端会瞬时回一个 0 状态，
  单次判定会把队列一首一首烧掉。
- 播放方式五种（顺序 / 列表循环 / 随机 / 单曲循环 / 只播这一首）。随机进度记录已播过去
  重、播完一轮自动重来；换一批曲目只清进度不清方式（说过「随机播放」之后切歌单还是随机）。
- 睡眠定时能按分钟也能按首数；按首数是在「这一首真的播完」时判的，不是设个闹钟。
- 队列、播放状态、定时、索引、监听、分组一并搭在 `/status.extra` 里回来，页面一次轮询
  喂满所有栏，而不是一栏一发请求。
- 设备分组：一条指令带动全组（播放、切曲、暂停、停止、音量、播报），全组共用一份队列 /
  方式 / 定时；成员互斥 —— 把设备挪进新组会从旧组摘走，旧组不足两台即作废。组内某台
  离线只追一条「卧室：设备离线」的告警，不让整次操作判失败：音箱各自经云端收指令，没有
  帧级同步，轻微起播时差属正常。默认音箱所在的那一组即「全屋广播」的落点。
- 定时任务：`weekly` 按星期几（0=周日）、`monthly` 按几号，到点执行播歌单 / 从某首歌播 /
  停止 / 设音量 / 设播放方式 / 开关语音监听。触发挂在既有的 20 秒巡检上并按分钟去重，
  同一分钟不会双发；执行日志留最近 200 条，`POST /tasks/run` 不等到点就能验证这条任务
  真能跑起来。目标可以是全部在线音箱、几台指定音箱或默认音箱，已被同组带动的成员不再
  作为独立目标各下发一次。

## 语音控制

`speech.py` + `voice.py` + `intents.py`：读小米的对话记录（M01 这类走 ubus 的
`nlp_result_get`）把说的话变成命令。

轮询是**三态**的：`None` 表示没读到（不推进时间基线，下轮重来）、`[]` 表示读到了但没有
新话、列表才是真的有新话 —— 把「读失败」当成「没说过」会把我没听见的话当成我说过，
这是这套东西最容易做错的一处。监听器自带节流与失败退避（最长退到 30 秒），说过话之后
的对话窗口内保持满速，追问才接得上。

口令表**用户可以自己改**（配置页「语音口令表」那一栏）：整类开关、把内置的某个说法单独
藏起来、加内置表里没有的说法。`POST /voice/test` 让任意一句话在**不接音箱**的情况下先看
出会被判成什么，加完口令就顺手判一次，当场知道接手不接手；执行覆盖点歌 / 歌手 / 专辑 /
歌单 / 收藏 / 随机 / 刚才那首 / 搜索 / 暂停 / 继续 / 停止 / 上下曲 / 按序号切曲 / 音量与
加减 / 静音 / 播放方式 / 定时停止 / 取消定时 / 查定时 / 播报。

自定义口令要带一个**内容**字段：内置的「播放歌曲 X」能自己吃掉后半句，新造的说法不能 ——
「播放周杰伦」判成播放歌手却带着空内容，什么也播不出来。所以点歌 / 歌手 / 歌单 / 按序号 /
播报这几类（还有音量的绝对值）必须填默认内容；说完整句后面还再带词的，用带的那个
（「播放周杰伦 稻香」播稻香），整句说完才回落到填的默认内容。校验：空串、纯标点、超过 20
字、类型不认识都拒；同一个词重复加不覆盖，回「已经加过了」。上限 60 条。
自定义词与内置词放在同一张表里按**最长关键词**抢，更长的那条赢，不需要额外的冲突规则。
改动落在 `<插件数据目录>/state/voice_words.json`（`{items:[{keyword,kind,param,argument}],
hidden:[…]}`），跟登录票据同一套 0600 文件存储。

判定是**三级**的：口令表 → 记忆表 → AI 兜底。侧栏「试一句话」的结果会标出这次是哪一级
接的手 —— 这决定了它稳不稳：口令表每次一样，记忆表跟着上一次的播放变，AI 兜底是问大模型
要的，同一句话两次可能给出不同结果。想把某句话变成确定的，就在口令表里给它加一条：
「播放周杰伦」这种不带「播放歌曲 / 我想听」的说法本来不在表里，只能落到第三级。
每次判定另记一行日志，页面上说不清的时候看日志。

近几轮的问答留在本机做指代（「换一首」「就要这个」）。口令判不出来时可选把这句话交给
**主程序已经配好的那个智能助手**（`app.agent.llm.LLMHelper`，读「设定 → AI 大模型」的
provider/model/key/base_url）判意图，或开自由对话；插件不再另配一份端点与密钥，宿主没配
就在配置页写明缺哪一项并退回到只用口令表。两个方向都只在显式开启时发出网络请求，用完
把模型实例交还宿主（`close_llm`）。

## 页面

- 侧栏 Vue3 页面（`./AppPage`）只看运行，不看配置：运行总览 / 播放台 / 音乐库 /
  歌单与收藏 / 定时任务 / 语音控制六栏，状态 5 秒轮询、页面隐藏时停；语音那一栏开着时
  跟着同一次轮询补读「听到了什么」。顶栏一次报出登录、在线音箱、监听、在播四件事，
  左侧导航带每栏的关键计数，栏与栏之间换一次淡入。详情页 `./Page` 是同一批接口的紧凑版
  （进度条 + 队列/在线/接手/曲库四格读数）。
- 定时任务栏是只读列表加「启停 / 立即执行」两个对当下状态的动作，任务定义本身（时间、
  动作、目标音箱）只在配置页改；口令表同理。改配置一律走页头的「插件配置」按钮弹出的
  配置页，对话框打开期间侧栏停轮询、关掉立刻补一次刷新；配置页每次保存都往外抛
  `updated`，所以侧栏跟得上身后的改动，不会出现两处显示两个值。
- 配置页（`./Config`）按「先做什么才有什么」排成六栏：账号与音箱 → 曲库与直链 →
  播放行为 → 语音与 AI → 语音口令表 → 定时任务。前三栏共用同一份表单草稿（草稿只有一份，
  所以它不进切栏动画，重建就等于丢掉没保存的值），页头的保存按钮只在草稿有变化时可点。
  「启用插件」与「在「发现」显示侧栏入口」是宿主记的开关，跟插件自己的 `enabled` 不是一
  回事，收在页头菜单里说明。
- `api.get` 只认第一个参数，`/browse`、`/search`、`/lyric`、`/playlist` 的条件由页面
  自己编码进 URL。配置页只发插件认识的字段（`/config` 缺省即保留原值）。
- 样式只写自己的类名与宿主 `--v-theme-*` 变量，深浅色都跟着主程序；构建的
  `.v-*` / `.mdi-*` 全局样式门禁一条不许命中。前端产物在 `dist/assets/`，与市场包
  一致才有效。

## 接口

`GET /status`、`/devices`、`/browse`、`/search`、`/lyric`、`/timer`、`/favorites`、
`/library`、`/playlists`、`/playlist`、`/voice`、`/commands`、`/groups`、`/tasks`、
`/tasks/logs`、`/config`、`/stream`；
`POST /login`、`/login/qrcode`、`/logout`、`/device/select`、`/play`、`/queue`、
`/control`、`/volume`、`/tts`、`/mode`、`/timer`、`/favorites`、`/library/refresh`、
`/voice/test`、`/commands`、`/groups`、`/tasks`、`/tasks/run`、`/config`。

除 `/stream`（`allow_anonymous`，靠签名与有效期）外都挂 `auth="bear"`。
`POST /login` 按登录方式给一种形状：`{}` 用配置里存好的账密发起、`{code:"…"}` 续跑那次
会话填码、`{resend:true}` 重新发起一次以拿新的短信/邮箱码、`{user_id:"…",pass_token:"…"}`
走 Cookie 票据。`POST /login/qrcode` 的 `{action:"start"}` 取二维码、`{action:"poll"}`
问一次结果，返回的 `state` 有 `qr_waiting` / `qr_expired` / `success` / `failed` 四种。
`GET /commands` 回内置表（每类的 `keywords`，含被藏起来的词与 `hidden` 列表）、
`customs`（用户加的说法）与 `kinds`（类型与子参数的中文名，页面拿它显示判定结果，前端不
再自己抄一份类型名）；`POST /commands` 每个字段都是**给了才改、没给不动**（`enabled` 传
`null` 不再顺手把整表打开），`add` / `remove` / `hide` / `unhide` 收关键词，`reset:true`
回到内置默认表。每次写入都回全表，页面直接用它刷新，不必再读一次。

## 排查

| 现象 | 先看 |
| --- | --- |
| 侧栏没有入口 | `enabled` 是否开着、`show_sidebar_nav` 是否关着；改过这两项要不要请宿主重建任务 |
| 每次重载或重启都要重新登录 | v0.5.8 及以前状态写宿主 `plugindata`，某些宿主会话不提交，票据与 deviceId 只活在进程里；v0.5.9 起落到 `<插件数据目录>/state/`，确认这个目录在持久卷上（容器里是 `/config/plugins/XiaoaiSpeaker/`） |
| 登录一直失败 | 按上表读那句原因；账密反复不过就切扫码，别硬碰风控 |
| 登录成功但没有音箱 | 票据失效或账号名下确实没有音箱，点「刷新设备」重试 |
| 点了没声音 / 音箱当电台放 | 先看日志那行「已推送 …」：接口、音频类型、设备、拉流地址与来源都在里面。型号该走 `player_play_music` 时把播放接口从 `auto` 改一下试 |
| 分不清「音箱没来」还是「来了不出声」 | 看有没有 `/stream 请求进来: …` 那行：**没有**就是音箱根本没访问到这个地址（网络/host/端口问题，跟格式与接口都无关）；**有**这行还不响，才轮到格式与接口（先切 `music`，再开「非 mp3 现场转成 mp3」） |
| 音箱拉不到直链（403/超时） | 外部访问地址是不是音箱可达的（填内网 IP:端口最稳；公网域名要看路由器支持 hairpin 与证书是否受信）、`stream_ttl` 是否太短、路径是否在库内 |
| 「签名不对或已过期」且日志里的文件名粘着 `exp=`/`sig=` | 链接被中间层改写了：小米云端会把 URL 里的 `&` 换成空格，多参数直链到音箱手里就是这么散的。现在整条链只有 `?k=` 一个参数、值是纯 ASCII 的 base64url，`&`/`%`/`+`/空格都不在里面 |
| 有 m4a/flac 却不出声 | `player_play_url` 只稳当吃 mp3，m4a（`audio/mp4`）与 flac 在多数型号上是「云端受理、设备不动」。先把播放接口从 `auto` 改 `music`（走设备自己的音乐管线，编码兼容好得多）；这条免费的路不通就打开「非 mp3 现场转成 mp3」，让 `/stream` 用本机 ffmpeg 现转成 mp3 |
| 语音口令不响应 | `voice_enabled`、监听设备是否包含这台、`/voice` 里 last_poll_at 有没有在动 |
| 同一句话两次判定不一样 | 它没进口令表，落到第三级 AI 兜底了 —— 大模型每次给的答案本来可能有出入。想要每次都一样，就去配置页给这句话加一条自定义口令（带「内容」）。侧栏「试一句话」的结果标签会写这次是谁判的，日志里也有一行 |
| 直链播放到一半断 | 连播判定依赖 20 秒巡检 + 两次读到停止，宽限期内不会续播 |
| 页面空白 / 组件加载错误 | `dist/assets/` 是否与 `remoteEntry.js` 里的分片名一致、市场包是否完整 |
| 换了文件但行为还是旧的 | 宿主的插件重载只重建实例、不重绑接口路由：`/status` 报的版本已经是新的，接口里跑的仍是进程启动时那份模块。手工替换文件后要重启主程序才算真的换掉（市场「更新」走的是重装路径，会重启到位） |
